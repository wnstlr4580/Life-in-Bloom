# [Design] 오행 포토부스 (키오스크)

> `오행포토부스.plan.md` 기반 상세 설계 — DB 스키마, API, 컴포넌트, 세그멘테이션·합성·네컷 스트립 파이프라인

---

## 1. 라우트 구조

기존 `(shop)` / `(admin)` 레이아웃과 분리된 신규 route group `(kiosk)`를 사용한다. 헤더/푸터/장바구니 등 쇼핑몰 UI를 전부 제거하고, 풀스크린·세로 모바일 전용 레이아웃으로 구성한다.

```
app/
├── (kiosk)/
│   ├── layout.tsx              # 풀스크린, 상단 네비 없음
│   └── kiosk/
│       └── page.tsx            # 인트로 → 생년월일 → 네컷 촬영 → 합성 → 결과, 한 페이지 내 step 상태 전환
├── (shop)/saju/page.tsx         # 기존 사주 페이지 — kiosk 딥링크 지원 추가 (아래 5번 참고)
└── api/kiosk/
    ├── photo/route.ts           # POST 업로드
    └── photo/[id]/route.ts      # GET 조회

```

세션 상태(생년월일 → 오행 → 촬영 이미지들)는 서버 저장 없이 클라이언트에서만 유지한다. `app/(kiosk)/kiosk/page.tsx` 하나에서 `step: "intro" | "birth" | "capture" | "processing" | "result" | "error"` 상태로 전체 플로우를 관리한다.

## 2. DB 스키마 (Prisma)

```prisma
// prisma/schema.prisma 에 추가

model KioskPhoto {
  id        String   @id @default(cuid())
  ohaeng    String   // "목" | "화" | "토" | "금" | "수"
  imageUrl  String   // Vercel Blob URL (네컷 스트립 이미지)
  createdAt DateTime @default(now())
  expiresAt DateTime // createdAt + 48h
}
```

- 생년월일은 DB에 저장하지 않는다 — 촬영 시점에 클라이언트가 이미 알고 있는 값이므로, QR URL의 쿼리 파라미터로 직접 전달한다 (아래 5번 참고). 얼굴 사진과 생년월일을 같은 레코드에 묶어 서버에 보관하지 않기 위한 선택이다.
- 런타임 조회는 기존 `app/api/saju/analyze`와 동일하게 Supabase JS client(`lib/supabase.ts`)로 처리한다.

## 3. API Routes

### 사진 업로드

| Method | Path | 설명 |
|--------|------|------|
| POST | `/api/kiosk/photo` | 합성된 네컷 스트립 이미지 + 오행 → Vercel Blob 업로드 + `KioskPhoto` 레코드 생성 |

```typescript
// POST /api/kiosk/photo (multipart/form-data: file, ohaeng)
// Response: { id: string, url: string }
```

### 사진 조회

| Method | Path | 설명 |
|--------|------|------|
| GET | `/api/kiosk/photo/[id]` | 만료 확인 후 `{ id, ohaeng, imageUrl }` 반환. 만료/미존재 시 404 |

이 엔드포인트는 더 이상 전용 다운로드 페이지가 아니라 **`(shop)/saju` 페이지가 클라이언트에서 호출**한다 (아래 5번 참고).

### 정리(Cleanup, 향후 과제)

만료된 `KioskPhoto` 레코드 + Blob 파일을 삭제하는 Vercel Cron은 이번 구현 범위에서는 보류 — plan 문서 Phase 7 참고.

## 4. 꽃 선정 — 4가지 모드 (2026-07-16 개편: 사주오행 제거)

포토부스는 오프라인 유입 채널이므로 사주 분석을 하지 않는다 — 사주는 QR로 연결되는 `/saju`의 역할. 대신 아래 4가지 모드로 꽃을 정한다 (`lib/kiosk/flowers.ts`).

| 모드 | 입력 | 선정 방식 |
|------|------|-----------|
| 생일꽃 | 생년월일 | 탄생화 테이블에서 MM-DD 조회 (미등록 날짜는 결정적 로테이션 대체). QR에 birthDate가 실려 /saju 자동 분석 연결 유지 |
| 오늘의 꽃 | 없음 | 연중 일수 기반 로테이션 — 같은 날 방문객은 같은 꽃 |
| 이달의 꽃 | 없음 | 영국식 birth month flower (monthFlower 컬럼) |
| 구매한 꽃 | 상품 바코드 스캔 | 판매처 재고 등록에 바코드값 추가 후 구현 예정 (현재 준비 중 비활성 버튼) |

## 5. 포토부스 꽃 테이블 (`lib/kiosk/kioskFlowers.json` + `flowerMeanings.json`) — 2026-07-16 개편

4가지 모드가 공용으로 쓰는 포토부스 전용 테이블. 현재 47종이며 탄생화 365종으로 확장 예정 (행만 추가하면 됨).

```
kioskFlowers.json  — id, species, color, name, engFlower,
                     birthDates[] (탄생화 날짜 MM-DD — 생일꽃),
                     monthFlower (1~12 | null — 이달의 꽃),
                     todayPool (오늘의 꽃 로테이션 후보 여부),
                     martFlower (플라워마트 판매꽃 여부 — 바코드 모드 대상),
                     background, frame (이미지 경로)
flowerMeanings.json — species + color → meaning, meaningEn (색깔별 꽃말, 검수 필요)
```

- 이달의 꽃 매핑은 영국식 목록을 보유 품종으로 대체한 초안 — 검수 필요
- 선택 로직: `pickBirthFlower(birthDate)` / `pickTodayFlower()` / `pickMonthFlower()` (`lib/kiosk/flowers.ts`)
- `/api/kiosk/photo`는 오행 대신 꽃 이름(`flower`)을 받으며, DB `KioskPhoto.ohaeng` 컬럼은 꽃 이름을 담는다 (컬럼 리네임 마이그레이션 예정)

배경·프레임 이미지는 런타임에 AI로 생성하지 않고 사전 생성·검수된 정적 이미지를 사용한다 (`public/kiosk-backgrounds/{id}.jpg`, `public/kiosk-frames/{id}.jpg`, 생성은 `scripts/generate-kiosk-backgrounds.mjs` — 키오스크는 속도·안정성 우선).

> 꽃말은 통상적으로 알려진 의미를 기준으로 선정했으며, 출처마다 조금씩 다르게 서술되는 경우가 있어 최종 문구는 콘텐츠 담당자의 검수를 권장한다.

## 6. 카메라 촬영 — 네컷 (`components/kiosk/CameraCapture.tsx`)

```
1. navigator.mediaDevices.getUserMedia({ video: { facingMode: "user" }, audio: false })
2. 첫 컷: 사용자가 "촬영 시작" 탭 → 3-2-1 카운트다운 → 캡처
3. 이후 3컷: 짧은 텀(약 1.2초)을 두고 자동으로 다음 카운트다운 시작 → 캡처
   (총 4컷, 컷 사이 카메라 스트림은 계속 유지 — 매번 재요청하지 않음)
4. 촬영 중에는 오행/꽃 정보를 노출하지 않는다 — "n / 4 컷" 진행 표시만 제공
5. 4컷 캡처 완료 시 ImageBitmap[] 4개를 부모(kiosk/page.tsx)에 전달, 카메라 스트림 정지
```

세그멘테이션·합성은 이 컴포넌트 책임이 아니라, 부모의 `processing` 단계에서 순차 처리한다 (관심사 분리).

> **테스트 모드 (임시 개발용, 2026-07-16)**: 인트로 화면의 "테스트 모드" 버튼은 생년월일 입력·카메라 촬영을 건너뛰고 고정 생일(1994-12-01)과 `public/kiosk-test/strip.png`을 4분할한 사진으로 합성 파이프라인을 실행한다. 검증이 끝나면 시작하기 흐름으로 대체·제거 예정.

## 7. 인물 분리 + 배경 합성 + 네컷 스트립 조립

### 7-1. 세그멘테이션 (`lib/kiosk/segmentation.ts`)

기존과 동일 — `@mediapipe/tasks-vision`의 `ImageSegmenter`(Selfie Segmenter)로 정지 프레임 1장의 인물 확률 마스크(0~1)를 추출한다. 4컷 모두 이 함수를 순차 호출한다 (`preloadSegmenter()`로 촬영 중 미리 모델을 로드해 처리 단계 지연을 줄인다).

### 7-2. 컷별 합성 (`lib/kiosk/compositeCanvas.ts` — `compositeSingleCut`)

```typescript
export async function compositeSingleCut(
  personImage: ImageBitmap,
  mask: Float32Array,
  backgroundUrl: string
): Promise<HTMLCanvasElement>
```

배경 이미지를 cover로 그린 뒤, 인물 레이어에 마스크값을 알파 채널로 적용해 합성한다 (기존 방식과 동일). 다만 이 단계에서는 뱃지/워터마크를 그리지 않는다 — 브랜딩은 스트립 조립 단계에서 한 번만 그린다.

### 7-3. 네컷 스트립 조립 (`buildFourCutStrip`) — 2026-07-16 개정

```typescript
export async function buildFourCutStrip(
  cuts: HTMLCanvasElement[], // 정확히 4장
  preset: KioskFlowerPreset
): Promise<Blob>
```

카드는 실제 인생네컷 인화지 비율 **600×1800 (1:3, 2×6인치)**:
1. 카드 배경 — 꽃 장식 프레임 이미지(`/kiosk-frames/{preset.id}.jpg`, 같은 600×1800 비율로 생성 필요). 없으면 크림 단색 대체
2. 흰 사진 패널(좌우 여백 40) 위에 4컷을 세로 배치 (셀 496×340, cover 크롭)
3. 하단 밴드(y≈1460~1800)에 날짜, 구분선(♡), 꽃말, "인생내꽃" 브랜드를 그림 — 오른쪽 아래는 QR 자리로 비워둠
4. JPEG `Blob`으로 변환해 반환

### 7-5. QR 스탬프 (`stampQrOnStrip`) — 2026-07-16 추가

```typescript
export async function stampQrOnStrip(stripBlob: Blob, url: string): Promise<Blob>
```

QR을 별도 위젯으로 띄우지 않고 카드 하단 오른쪽에 직접 그린다. `buildFourCutStrip()` 시점에는 QR 대상 URL(업로드 응답의 사진 id)이 없으므로, ResultShare가 업로드 완료 후 이 함수로 다시 굽는다. 업로드된 원본(= `/saju`에서 저장하는 사진)에는 QR이 없다.

### 7-4. 처리 흐름 (`app/(kiosk)/kiosk/page.tsx`)

```typescript
for (const image of capturedImages) {
  const mask = await segmentPerson(image)
  const cut = await compositeSingleCut(image, mask, backgroundUrl)
  cuts.push(cut)
  setProcessingProgress(p => p + 1) // n / 4 진행률 표시
}
const stripBlob = await buildFourCutStrip(cuts, ohaeng)
```

## 8. 결과 공개 + QR (`components/kiosk/ResultShare.tsx`)

```
1. buildFourCutStrip() 결과 Blob을 미리보기로 표시 — 이 순간 처음으로 오행/꽃/꽃말을 공개
2. 자동으로 POST /api/kiosk/photo (FormData: file, ohaeng) 호출
3. 응답의 id로 QR 대상 URL 구성:
   `${origin}/saju?birthDate=${birthDate}&kiosk=${id}`
   (다운로드 전용 페이지가 아니라 기존 /saju 페이지로 딥링크)
4. stampQrOnStrip()으로 QR을 스트립 하단 오른쪽에 합성해 미리보기를 교체
   (별도 QR 위젯 없음 — 2026-07-16 개정. PC 테스트용 "웹페이지 바로가기" 소형 링크만 유지)
5. "다시 촬영하기"(4컷 전체 재촬영) / "처음으로" 버튼 제공
6. 결과 화면 진입 후 60초 유휴 시 자동으로 인트로(step="intro")로 복귀
```

## 9. `/saju` 페이지 딥링크 연동 (`app/(shop)/saju/page.tsx`)

QR로 도착한 방문객은 기존 사주 결과 페이지를 그대로 이용한다 — 별도의 축소된 결과 페이지를 새로 만들지 않고, 아래 두 가지만 기존 페이지에 추가한다.

### 9-1. 쿼리 파라미터

- `birthDate`: 키오스크에서 입력받은 생년월일 (`YYYY-MM-DD`)
- `kiosk`: 업로드된 `KioskPhoto`의 id

`useSearchParams()`를 사용하므로 페이지 컴포넌트를 `<Suspense>`로 감싼다.

### 9-2. 자동 분석

```typescript
useEffect(() => {
  if (!kioskBirthDate || kioskAutoSubmitted.current) return
  kioskAutoSubmitted.current = true
  handleSubmit({
    name: "", gender: "female", birthDate: kioskBirthDate,
    birthHour: "unknown", city: "미입력", calendarType: "solar",
  })
}, [kioskBirthDate, handleSubmit])
```

폼 입력 없이 즉시 1차 분석 결과(오행, 오늘의 운세, 오행 밸런스, 추천 꽃)를 보여준다. 이때 `BirthDateForm`의 `defaultValues`에도 동일한 생년월일을 채워 넣어, 폼이 그대로 보이는 상태에서 이름·시간을 추가 입력해 재제출하면 시주까지 포함한 더 정확한 결과로 갱신할 수 있다 (기존 "저장된 정보 불러오기" 메커니즘과 동일한 `defaultValues` prop을 재사용).

### 9-3. 키오스크 사진 표시

```typescript
useEffect(() => {
  if (!kioskPhotoId) return
  fetch(`/api/kiosk/photo/${kioskPhotoId}`)
    .then(r => { if (!r.ok) throw new Error(); return r.json() })
    .then(setKioskPhoto)
    .catch(() => setKioskPhotoExpired(true))
}, [kioskPhotoId])
```

페이지 상단에 촬영한 네컷 썸네일 + "저장" 다운로드 링크를 표시. 만료된 경우 안내 문구로 대체. 기존 `ShareCard`(SNS 공유용 자동 생성 카드)는 그대로 유지 — 실물 네컷 사진과는 별개 콘텐츠라 함께 두어도 겹치지 않는다.

### 9-4. 비-키오스크 사용자 영향

쿼리 파라미터가 없는 일반 방문(폼 직접 입력)은 기존 동작과 완전히 동일하다 — 이번 변경은 전부 `kioskBirthDate`/`kioskPhotoId` 존재 여부로 조건부 분기된다.

## 12. 성공 기준 (Design 기준)
