# [Design] 판매처 등록 및 역할별 계정
> `판매처등록.plan.md`의 Supabase 데이터 모델, 인증, 접근 제어, 화면 및 API 상세 설계

## 1. 설계 원칙

- NextAuth는 인증을 담당하고 Supabase PostgreSQL의 `User.role`이 권한의 기준이다.
- Supabase `service_role`은 서버 API에서만 사용하고 브라우저에 노출하지 않는다.
- 화면 숨김이 아니라 모든 서버 API에서 역할과 판매자 승인 상태를 검사한다.
- 판매자 가입 정보와 공개 판매처 정보, 심사 이력을 분리한다.
- 민감한 사업자 증빙은 Supabase Storage 비공개 버킷에 저장하고 관리자용 서명 URL로만 조회한다.

## 2. 데이터 모델

### Enum

```prisma
enum UserRole {
  CUSTOMER
  SELLER
  ADMIN
}

enum SellerStatus {
  PENDING
  UNDER_REVIEW
  APPROVED
  REJECTED
  SUSPENDED
}

enum SellerType {
  FLOWER_SHOP
  FARM
  WHOLESALE
  OTHER
}
```

### User

```prisma
model User {
  id       String   @id @default(cuid())
  email    String   @unique
  role     UserRole @default(CUSTOMER)
  // 기존 일반회원 필드 유지

  seller       Seller?
  adminActions SellerReview[] @relation("SellerReviewer")
}
```

기존 `isAdmin`은 마이그레이션 시 `role = ADMIN`으로 변환한 뒤 제거한다.

### Seller

```prisma
model Seller {
  id                    String       @id @default(cuid())
  userId                String       @unique
  status                SellerStatus @default(PENDING)

  legalBusinessName     String
  businessNumber        String       @unique
  representativeName    String
  businessType          String
  businessCategory      String
  mailOrderNumber       String?

  marketName            String
  sellerType            SellerType
  managerName           String
  managerPhone          String
  publicPhone           String?
  introduction          String?
  logoUrl               String?
  businessLicensePath   String

  postalCode            String
  roadAddress           String
  detailAddress         String
  latitude              Decimal      @db.Decimal(10, 7)
  longitude             Decimal      @db.Decimal(10, 7)
  businessHours         Json?

  settlementBank        String
  settlementAccount     String
  settlementHolder      String

  sellsFinishedProducts Boolean      @default(true)
  offersCustomBouquet   Boolean      @default(false)
  offersDiyFlowers      Boolean      @default(false)
  isOpen                Boolean      @default(true)

  termsVersion          String
  termsAgreedAt         DateTime
  submittedAt           DateTime     @default(now())
  approvedAt            DateTime?
  createdAt             DateTime     @default(now())
  updatedAt             DateTime     @updatedAt

  user       User           @relation(fields: [userId], references: [id])
  reviews    SellerReview[]
  stocks     SellerStock[]
  products   Product[]
}
```

서비스 참여 여부는 판매자가 자유롭게 바꾸는 운영 설정이므로 `Seller`에 둔다. 가입 시 받은 초기 선택값으로 생성하고, 승인 후 설정 화면에서 갱신한다.

### SellerReview

```prisma
model SellerReview {
  id           String       @id @default(cuid())
  sellerId     String
  reviewerId   String?
  fromStatus   SellerStatus?
  toStatus     SellerStatus
  reason       String?
  snapshot     Json
  createdAt    DateTime     @default(now())

  seller       Seller       @relation(fields: [sellerId], references: [id])
  reviewer     User?        @relation("SellerReviewer", fields: [reviewerId], references: [id])
}
```

별도의 현재 상태용 `SellerApplication`을 중복 생성하지 않고 `Seller`가 현재 신청 상태를 가진다. 제출·재제출·승인·반려 기록은 `SellerReview.snapshot`에 당시 신청서 스냅샷으로 남긴다.

### SellerStock

```prisma
model SellerStock {
  id          String   @id @default(cuid())
  sellerId    String
  flowerCode  String
  flowerName  String
  color       String?
  grade       String?
  unit        String   @default("STEM")
  quantity    Int
  unitPrice   Int
  barcode     String?
  isActive    Boolean  @default(true)
  updatedAt   DateTime @updatedAt

  seller      Seller   @relation(fields: [sellerId], references: [id])

  @@unique([sellerId, flowerCode, color, grade])
  @@index([flowerCode, isActive])
}
```

### Product 연결

```prisma
model Product {
  // 기존 필드 유지
  sellerId String?
  seller   Seller? @relation(fields: [sellerId], references: [id])

  @@index([sellerId, isActive])
}
```

기존 상품은 마이그레이션 시 인생내꽃 운영 판매처를 하나 생성해 연결하거나, 전환 기간 동안 `sellerId = null`을 플랫폼 직영 상품으로 취급한다.

## 3. Supabase 마이그레이션

실제 운영 DB 변경은 Prisma 명령만으로 가정하지 않고 재실행 가능한 SQL 파일로 작성한다.

1. enum과 신규 테이블 생성
2. `User.role` 추가
3. 기존 `isAdmin = true`를 `ADMIN`으로 변환
4. 기존 사용자는 `CUSTOMER`
5. `Product.sellerId` nullable 추가
6. 인덱스·외래키·중복 제약 추가
7. 비공개 `seller-documents` Storage 버킷과 정책 설정

관리자 승격 예시:

```sql
UPDATE "User"
SET "role" = 'ADMIN'
WHERE "email" = 'owner@example.com';
```

이 SQL은 최초 관리자 부트스트랩 용도로만 사용한다. 이후 변경은 관리자 API와 감사 로그를 통한다.

## 4. 인증과 세션

NextAuth JWT와 session에 아래 값을 담는다.

```ts
session.user = {
  id,
  email,
  name,
  image,
  role,          // CUSTOMER | SELLER | ADMIN
  sellerStatus,  // 판매자만 존재
}
```

- 소셜 로그인으로 처음 생성되는 계정은 항상 `CUSTOMER`
- `/api/auth/signup/customer`는 항상 `CUSTOMER`
- `/api/auth/signup/seller`는 항상 `SELLER`와 `Seller(PENDING)`를 하나의 서버 트랜잭션으로 생성
- 클라이언트가 보낸 `role`, `status`, `approvedAt` 값은 무시
- 판매자 로그인은 credentials provider를 공유하되 역할에 따라 이동

## 5. 접근 제어

| 영역 | 조건 |
|---|---|
| `/mypage`, 구매자 API | `role = CUSTOMER` |
| `/seller` 심사 상태 | `role = SELLER` |
| 판매자 상품·재고·주문 API | `role = SELLER` 및 `status = APPROVED` |
| `/admin`, 관리자 API | `role = ADMIN` |

공통 서버 가드를 둔다.

```ts
requireCustomer()
requireSeller()
requireApprovedSeller()
requireAdmin()
```

로그인 후 이동:

```text
CUSTOMER → /mypage
SELLER   → /seller
ADMIN    → /admin
```

## 6. API

| Method | Path | 권한 | 기능 |
|---|---|---|---|
| POST | `/api/auth/signup/customer` | 공개 | 일반 이메일 가입 |
| POST | `/api/auth/signup/seller` | 공개 | 판매자 계정·신청서 생성 |
| GET | `/api/seller/profile` | 판매자 | 판매처·심사 정보 조회 |
| PATCH | `/api/seller/profile` | 승인 판매자 | 공개 판매처 정보 수정 |
| PATCH | `/api/seller/services` | 승인 판매자 | 서비스 참여 여부 변경 |
| GET/POST/PATCH | `/api/seller/products` | 승인 판매자 | 자기 완제품 관리 |
| GET/POST/PATCH | `/api/seller/stocks` | 승인 판매자 | 자기 개별 꽃 재고 관리 |
| GET | `/api/admin/sellers` | 관리자 | 신청 목록 |
| GET | `/api/admin/sellers/[id]` | 관리자 | 신청·증빙 상세 |
| POST | `/api/admin/sellers/[id]/review` | 관리자 | 검토중·승인·반려·정지 |
| POST | `/api/admin/users/[id]/role` | 관리자 | 관리자 권한 부여·회수 |

판매자 가입 API는 계정만 생성되고 판매처 생성이 실패하는 상태를 막기 위해 PostgreSQL 함수(RPC) 또는 서버 트랜잭션으로 원자 처리한다.

## 7. 화면

### `/signup`

일반 사용자와 판매자 카드 두 개를 보여준다. 판매자 카드에는 “사업자·판매처 정보 제출 후 승인이 필요합니다”를 명시한다.

### `/signup/seller`

긴 단일 폼 대신 단계형으로 구성한다.

1. 계정·담당자
2. 사업자 정보와 증빙
3. 마켓명·주소·위치
4. 정산 정보
5. 서비스 참여와 약관
6. 입력 내용 확인·제출

사업자등록번호, 담당자 연락처, 계좌번호는 화면에서 다시 표시할 때 마스킹한다.

### `/seller`

- `PENDING`: 접수 완료와 예상 처리 안내, 제출 정보 확인
- `UNDER_REVIEW`: 검토 중 안내, 핵심 정보 수정 제한
- `REJECTED`: 반려 사유와 재제출
- `APPROVED`: 판매자 대시보드
- `SUSPENDED`: 정지 사유와 문의 안내

### `/seller/settings/services`

```text
[토글] 완제품 판매
[토글] 나만의 꽃다발 주문하기에 내 판매처 노출
[토글] 직접 만든다면?에 내 판매처 노출
```

토글 아래에 재고가 없으면 실제 노출되지 않는다는 조건을 표시한다. 끄기 전에는 진행 중 주문에는 영향이 없고 신규 주문·매칭만 중단된다는 확인 문구를 보여준다.

## 8. 서비스 매칭 규칙

### 나만의 꽃다발 주문하기

후보 판매처:

```text
status = APPROVED
AND isOpen = true
AND offersCustomBouquet = true
AND 선택 꽃과 SellerStock의 교집합이 존재
```

매칭 순위는 재고 충족률, 사용자와의 거리, 예상 가격을 기준으로 후속 구현한다.

### 직접 만든다면?

후보 판매처:

```text
status = APPROVED
AND isOpen = true
AND offersDiyFlowers = true
AND 요청한 개별 꽃 재고가 존재
```

판매처별 보유 꽃, 예상 재료비, 거리와 픽업 가능 여부를 노출한다.

## 9. 검증 기준

- 소셜 가입으로 `SELLER` 또는 `ADMIN`이 생성되지 않는다.
- 일반 사용자가 판매자·관리자 API를 호출하면 403이다.
- 미승인 판매자가 상품·재고 API를 호출하면 403이다.
- 판매자 가입 도중 실패하면 `User`만 남지 않는다.
- 관리자 승인·반려·권한 변경 이력이 남는다.
- 서비스 참여를 끄면 신규 노출에서 빠지고 기존 주문은 유지된다.
- 판매자는 다른 판매자의 상품·재고·주문을 조회하거나 수정할 수 없다.
- 일반회원의 기존 오행 정보 입력·수정·조회가 그대로 동작한다.
